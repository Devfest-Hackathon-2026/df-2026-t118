# 一括自動実装（放置用）

引数: `$ARGUMENTS`（イシュー番号。省略可。複数可）

ユーザーは不在（寝ている）ものとして、**一切確認を取らずに**実行し、最後に1回だけ報告する。

このファイルには**親（オーケストレーター）の手順だけ**を書く。各作業の手順は役割別ファイルにあり、**サブエージェントには該当ファイル1つだけを読ませる**（全体を読ませない。トークンの節約）。

| 役割 | ファイル |
| --- | --- |
| レビュー（メンバーのPR。指摘なしならマージ） | `.claude/sleep/review.md` |
| マージ確認（自分がレビュー済みのPR） | `.claude/sleep/merge-check.md` |
| コンフリクト解消（自分のPR） | `.claude/sleep/conflict.md` |
| 実装・レビュー対応（イシュー） | `.claude/sleep/implement.md` |
| 共通規則（マージ条件・レビュー観点・ラベル） | `.claude/shared/rules.md` |

## 原則

- **質問しない・許可を待たない**。`AskUserQuestion` は使わない。迷ったら安全側（破壊的でない・外部に影響しない側）を選び、その判断を最終報告に書く。
- **技術選定が必要になったら実装しない**。`AGENTS.md` の「人間が決定するまで実装を始めない」が優先される。ライブラリ・フレームワーク・データモデル・外部サービスの選択が未決定のまま必要になった場合は、候補と pro/con を最終報告に出して人間の判断に委ね、そのイシューは `failed` ではなく `skipped` に記録する。
- 投稿してよいのは次の4つだけ。それ以外のPR・イシューへは投稿しない。
  - 自分のPRへのレビュー対応報告
  - メンバーのレビュー待ちPRへのレビュー
  - 自分がレビューしたPRの対応確認結果
  - 自分のPRのコンフリクト解消の報告
- マージしてよいのは次の3つだけ。いずれも `.claude/shared/rules.md` のマージ条件を満たすこと。
  - 自分がレビューしたPRで、指摘の対応を確認できたもの（`merge-check.md`）
  - 自分がレビューして「指摘なし」だったPR（`review.md`）
  - コンフリクトを自分で解消して push した自分のPR（`conflict.md`）。コンフリクトと無関係の自分のPRはマージしない
- 破壊的な操作（force push、他人のブランチの書き換え、未 push の変更を含む worktree の削除、ブランチの削除、イシューのクローズ・編集）はしない。
- `.env` と認証情報には触れない。生成・コミットもしない。
- **状態ラベル**（`status::wip` / `status::reviewing`。運用は `.claude/shared/rules.md`）の付け替えは投稿に数えない。メンバーのPRにも行ってよい。作業を終えるとき（成功・失敗・中断のどれでも）、自分が付けたラベルを必ず外す。
- 他のメンバーが担当のイシュー、前提が未完了のイシューは実装しない。

## サブエージェントの起動規約

- プロンプトは**短く**する。含めるのは、(1) 役割ファイルのパス（「`.claude/sleep/<役割>.md` を読んで、その手順を実行せよ」）、(2) 対象（PR番号 / イシュー番号とモード）、(3) 原則の要約（質問しない・破壊的操作をしない・投稿してよい範囲・技術選定が必要なら中断）、(4) 報告は役割ファイルの「返す報告」の形で短く、の4つだけ。手順を親が書き写さない。
- **モデル**: 判断の軽い定型作業（`merge-check`）は軽いモデルを指定してよい。`review` / `implement` / `conflict` は指定せず親と同じモデルで動かす。
- **同時実行は最大3つ**。バッチではなく**ローリング**で回す（完了通知を受けるたびに次の対象をすぐ起動する）。
- **起動順**: 長い `implement` を先に、そのあと `review` → `merge-check` → `conflict`。マージで前提が解消されたイシューは**次のラウンド**で扱う。

## 0. ラウンドのループ

### 0a. main の最新化（各ラウンドの最初）

- `git status --porcelain` と `git branch --show-current` を確認する。
- main かつ未コミットの変更がなければ `git pull --ff-only origin main`。
- それ以外は `git checkout` / `git switch` をせず `git fetch origin` だけ行い、**最終報告に1回だけ**「main を更新できなかった（理由）」と書く。
- `--ff-only` が失敗した場合も merge / reset はせず、最終報告に書いて続行する。
- pull で `.claude/` の内容が**実際に変わった**ときだけ、変わったファイルを読み直す。
- **最初のラウンドだけ**、自分が付けて残っている `status::wip` / `status::reviewing` を外す。他のメンバーが付けたラベルには触れない。

### 0b. 終了条件

手順 1〜3 を **1ラウンド** とする。次のいずれかでループを終え、手順 4 の最終報告をする。

- **対象が完全になくなった**: 手順 1 でレビュー・マージ確認・コンフリクト・実装のすべてが0件。
- **このラウンドでマージが1件もなかった**: 新しい対象が生まれるのは main が進んだときだけ。レビューの投稿・PR作成・push だけでは、作成者が不在の間は状況が変わらないため、次のラウンドは空振りになる。
- **ラウンド上限**: 5ラウンド（ハッカソンの夜1回分を想定。長く回す場合は増やす）。上限で止まった場合は残っている対象を最終報告に書く。

マージが1件以上あれば 0a に戻る。

### 0c. 状態ファイル

ラウンド数・対応済み・失敗の記録は、コンテキストが要約されても失われないよう、**スクラッチパッドディレクトリ**（システムプロンプトで指定された、このセッション専用のディレクトリ）の `sleep-state.json` に書く。git 管理下に置かない。

```json
{
  "round": 2,
  "reviewed": [{"pr": 12, "headSha": "abc123", "merged": false}],
  "merge_checked": [{"pr": 9, "headSha": "def456", "merged": false}],
  "merged": [7],
  "created": [{"issue": 30, "pr": 41}],
  "conflict_resolved": [{"pr": 41, "headSha": "789abc", "merged": true}],
  "conflict_unresolved": [{"pr": 43, "headSha": "456def", "reason": "双方の意図が両立しない"}],
  "ci_pending": [{"pr": 15, "headSha": "aaa111"}],
  "failed": [{"issue": 31, "reason": "テストが通らない"}],
  "skipped": [{"issue": 35, "reason": "技術選定が未決定（エージェント基盤）"}],
  "issue_requires": {"30": {"updatedAt": "2026-11-05T10:00:00Z", "requires": [34, 38]}}
}
```

- 最初のラウンドの開始時にファイルがなければ作る（`round: 0`）。あれば読み込む（要約後の再開を含む）。
- 各ラウンドの開始時に読み、手順 1 の対象から次を除く。
  - `reviewed` / `merge_checked` / `ci_pending` / `conflict_unresolved` のPRのうち、現在の head SHA が記録と同じもの（新しい commit がない。main が進んだだけでは再試行しない）。自分のコメントは「更新」に数えない。
  - `failed` のイシュー（再実行しない）。
- `issue_requires` はイシュー本文の `前提:` 行の解析結果のキャッシュ。`updatedAt` が変わらないイシューは本文を取り直さない。前提がオープンかどうかは毎ラウンド確認する。
- サブエージェントの報告を受けるたびに追記する（ラウンドの終わりまで待たない）。
- 最終報告はこのファイルの内容から作る。

## 1. 対象の特定

**出力は必要な項目だけに絞る**（`--jq` / `jq`）。レビュー本文やイシュー本文を全件、毎ラウンド取得しない。

### 1a. レビュー待ちPR

```bash
ME=$(gh api user --jq .login)
gh pr list --state open --limit 200 \
  --json number,title,author,headRefName,headRefOid,isDraft,updatedAt,labels,reviews \
| jq --arg me "$ME" '[.[]
    | select(.author.login != $me and (.isDraft | not))
    | {number, title, author: .author.login, headRefOid, updatedAt,
       labels: [.labels[].name],
       myReviewAt: ([.reviews[] | select(.author.login == $me) | .submittedAt] | max)}]'
```

- **レビュー対象**: `myReviewAt` が null → `review.md`
- **マージ確認の対象**: `myReviewAt` があり、`updatedAt` がそれより新しい → `merge-check.md`
- **対象外**: 自分がレビュー済みで、その後の更新がない

`status::reviewing` が付いていて、他のメンバーが作業中と判断できるもの（`.claude/shared/rules.md` の判定）は、このラウンドの対象から外す（報告に書く）。

### 1b. 実装対象イシュー

1. 自分が担当のオープンなイシューを本文なしで取得する。
   `gh issue list --state open --assignee @me --limit 200 --json number,title,labels,updatedAt`
   - 0件なら、担当者のいないイシューは**実装しない**。その旨を記録し、実装側は行わない（他は続ける）。
2. 本文は、`issue_requires` にない、または `updatedAt` が変わったイシューだけ取得する。
   `gh issue view <番号> --json body --jq .body` の `前提: #34、#38` 行から前提を抜き出してキャッシュする。
3. 前提のオープン判定は1回で行う。
   `gh issue list --state open --limit 200 --json number,assignees`
   - **着手可能**: 前提がすべてクローズ済み
   - **自分の前提待ち**: オープンな前提がすべて自分の担当
   - **他の人待ち**: オープンな前提に他のメンバー担当、または担当者なしのものがある
4. **対象は「着手可能」なものすべて**。引数で番号が指定された場合は、そのうち「着手可能」なものだけ（前提が未完了のものは対象外にして報告に書く）。
5. 「着手可能」以外は、待っている前提と担当者を `skipped` に記録する。

対象ごとに、対応するオープンなPRを探す（この結果は 1c でも使い回す）。

```bash
gh pr list --state open --limit 200 --json number,headRefName,author,headRefOid,mergeable,closingIssuesReferences
```

- PRがあり、レビューが投稿されている（`gh pr view <番号> --json reviews,comments` と `gh api repos/{owner}/{repo}/pulls/<番号>/comments`） → **レビュー対応モード**。Gemini Code Assist のレビューも対応対象に含める。
- PRがあり、レビューがない → 対応中なので**スキップ**（報告に書く）。
- PRがない → 通常モード。

### 1c. コンフリクトしている自分のPR

上で取得した一覧から、`author` が自分で `mergeable` が `CONFLICTING` のものを集める → `conflict.md`。`UNKNOWN` は少し待って1回だけ取り直し、それでも `UNKNOWN` ならこのラウンドでは対象外にする。

1b のレビュー対応モードの対象PRは `implement.md` 内でコンフリクトも解消するため、1c から除く（同じPRを二重に起動しない）。

## 2. 並列で実行

「サブエージェントの起動規約」に従って対象ごとに起動する。

- `implement` ← 1b の対象イシュー（モードも渡す）
- `review` ← 1a のレビュー対象PR
- `merge-check` ← 1a のマージ確認の対象PR
- `conflict` ← 1c の対象PR

同じファイルを複数のサブエージェントが編集し、マージ時に衝突しうることは想定済み。事前に調整しようとせず、その旨を最終報告に書く。

## 3. 後片付け（各ラウンドの最後）

全サブエージェントの完了後、確認なしで次を行う。

- レビュー用 worktree は各担当が削除済みのはず。残っていれば報告する。
- 実装用 worktree: 変更がすべて commit・push 済み（`git -C ../hannari-<番号> status --porcelain` が空で `git log origin/<ブランチ名>..HEAD` も空）のものだけ `git worktree remove ../hannari-<番号>` で削除する。そうでないものは残して報告する。
- 実装中に起動した捨てコンテナ・エミュレータのうち、サブエージェントが自分で起動したと報告したものだけ停止する。
- ブランチは削除しない（PR が参照している）。

## 4. 最終報告

全ラウンド分をまとめて**1回だけ**、朝に読む前提で簡潔に書く（状態ファイルから作る）。表は該当がある場合だけ載せる。

- レビューしたPR（URL・作成者・指摘の要約・「指摘なし」でマージしたか、しなかった理由）
- マージ確認したPR（URL・作成者・各指摘の対応状況・マージしたか、しなかった理由）
- 作成・更新したPR（イシュー番号・URL・モード・テスト結果）
- コンフリクトを扱った自分のPR（URL・対象ファイル・解消方針・push したか・マージしたか）
- スキップ・対象外にしたイシューとその理由（前提待ち、既存PRで対応中、技術選定が必要、など）
- **技術選定が必要で止めた項目**（候補と pro/con。朝いちで決められる形にする）
- 質問せずに自分で判断した点
- 未解決事項、残した worktree、マージ時に衝突しそうな箇所
- 次にやるとよいこと（今回のPRがマージされると着手可能になるイシューなど）
