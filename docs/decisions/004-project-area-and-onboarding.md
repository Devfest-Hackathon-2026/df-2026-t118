# ADR-004: 初回アンケートによる Project / Area 把握、保存直後の紐づけ、夜の提案型クラスタリング、およびホーム表示時の今日の一歩生成

- 日付: 2026-11-07
- 状態: 承認
- 決定者: チーム（Michi）

## 背景

[ADR-003](003-backend-and-data-model.md) では「すべての未確定保存物をまず Someday に保存し、夜 23:00 に類似意図を Bundle に束ね、朝 08:00 に 1 提案を出す」構造を採用していた。
その後、チームの要件整理（F01〜F05 / R01〜R07）により、以下の体験を既存の 3D 島・Bundle 体験と両立させる必要が生じた：

1. **初回アンケート（F01）**: ユーザーが現在進めている **Project（取り組み名＋目的）** と継続して大切にしたい **Area（生活・責任の領域）**、よく保存するもの（関心）、しまへの期待を初回オンボーディング（全問スキップ可・設定画面でいつでも編集可）で把握し、初期クラスターとして保持する。
2. **保存直後の意図確認と Project / Area 紐づけ（F02 / F03）**:
   - AI 送信前の同意確認（初回のみ・設定で変更可、拒否時は手動保存・分類可）。
   - URL 取得失敗時は読めたふりをせず「内容を取得できませんでした（URL のみ保存・補足メモ可）」と明示する（R04）。
   - 意図確認では AI 3 候補・自由入力に加え、**「見るだけ・参考（→ Resources）」** と **「あとで（→ いつか箱 Someday）」** を選べるようにする。
   - 確定した意図と既存のアクティブな Project / Area を照合し、保存直後に紐づけ（明確一致なら 1 件へ紐づけ＋変更ボタン、複数候補なら選択 UI、不明ならいつか箱へ保留）できるようにする。
3. **夜の自動クラスタリングの提案・承認型化（F5 拡張）**:
   - 既存の「束ねる（夜）」ボタンおよび定時処理を残しつつ、未整理・保留の保存物を自動でクラスタリングして Project / Area への振り分け案（または新規束案）を作成し、**提案型（承認待ち）** としてユーザーがワンタップで承認・変更できるようにする。
4. **ホーム表示時の「今日の一歩」オンデマンド生成（F05 / F6 統合）**:
   - 既存の「今日の一歩（朝）」ボタンも残しつつ、ホーム画面を開いたときに当日（ユーザーの IANA タイムゾーンにおける現地日付 `localDate`）の提案がまだなければ、実行可能な確定意図を持つアクティブな Project（または承認済み束）から 1 日最大 1 件の「今日の一歩」を自動生成する。
   - `done` の記録時のみ島の建物が成長し、連打やリロードで二重成長しない冪等性を担保する。

## 候補と比較

| 観点 | 候補A: ハイブリッド統合方式（初回アンケート + 保存直後 Project/Area 紐づけ + 夜の提案型クラスタリング + ホーム表示時 1 日 1 提案） | 候補B: Project/Area 完全移行方式（Bundle・夜ボタンを廃止し手動 Project 紐づけに一本化） | 候補C: 現行 Bundle 優先方式（初回アンケートで枠だけ作り、保存直後紐づけは行わない） |
|---|---|---|---|
| 学習コスト | 低（既存の 4 層レイヤードアーキテクチャをそのまま拡張） | 低 | 最低 |
| 実装速度 | 高（既存の `SavedItem` / `Bundle` / `Proposal` スキーマと下位互換を保ちつつ拡張可能） | 中（3D 島の Bundle スポット連動を作り直す必要がある） | 最高（変更最小） |
| Google 製品との相性 | 高（Gemini 構造化出力 + `text-embedding-004` + Firestore + Cloud Storage をそのまま活用） | 高 | 高 |
| コスト | 無料枠〜数円（同日 `localDate` で 1 日 1 提案に制限するため Gemini 呼び出し回数も抑制） | 無料枠〜数円 | 無料枠〜数円 |
| デプロイ容易性 | 高（既存の Firebase Hosting + Cloud Functions 構成のまま配信可能） | 高 | 高 |
| 情報量 | 十分（F01〜F05 の受け入れ条件と既存の 3D 島演出の両方を満たす） | 不足（夜の自動整理の魅力が消える） | 不足（F03 の保存直後 Project/Area 紐づけ要件を満たせない） |

## 決定

**候補A（ハイブリッド統合方式）** を採用する。

1. **ドメインモデルの拡張（下位互換維持）**:
   - `UserProfile`: `onboardingCompleted`, `aiConsentGranted`, `aiConsentAt`, `timezone`, `pendingTimezone`, `interests: string[]`, `expectations: string[]` を保持する。
   - `Project` / `Area` エンティティ（`id`, `name`, `goal?`, `status: 'active' | 'archived'`, `buildingLevel`, `createdAt`, `updatedAt`）を導入しつつ、既存の `Bundle` に `approvalStatus: 'pending' | 'approved'` および `targetProjectId?` / `targetAreaId?` を持たせることで、3D 島のスポット・建物描画と完全互換を保つ。
   - `SavedItem`: `intentStatus: 'pending' | 'confirmed' | 'reference'`, `placementKind: 'project' | 'area' | 'resource' | 'someday' | 'archive'`, `placementId: string | null`, `urlFetchStatus?: 'ok' | 'failed' | 'skipped'` を追加し、既存の `para` / `bundleId` と双方向同期する。
   - `Proposal`: `localDate`（`YYYY-MM-DD`）と `timezoneAtCreation` を持たせ、同日・同一ユーザーで最大 1 件の冪等性を保証する。
2. **URL 取得の安全性と失敗明示（R04）**:
   - プライベート IP・ループバック・メタデータ IP の拒否、HTTP/HTTPS スキーム限定、タイムアウト 4 秒、サイズ上限を維持した上で、取得失敗時（または Instagram 等の動的ページで本文が取れない場合）は `urlFetched: false` を返し、UI 上で「ページの本文は取得できなかったため URL のみ保存します（補足メモを入力できます）」と明示する。
3. **保存物の完全削除と Archive 復元（R03 / T19 / P1）**:
   - Archive は削除と区別し、ワンタップで元の置き場へ復元可能とする。
   - 削除操作時は Firestore ドキュメントと Cloud Storage 画像の両方を削除し、既存提案が参照していた場合は「削除済み資料」として安全に扱う。

## 根拠

- チームで整理した F01〜F05・R01〜R06 のすべての受け入れ条件（4 問アンケート、AI 同意、「見るだけ・参考」、保存直後の Project/Area 照合、同日 1 提案の冪等性、削除・復元）を満たしながら、これまでに実装した 3D 島の演出や「束ねる（夜）」「今日の一歩（朝）」の操作性もそのまま活かせるため。

## 却下した案と理由

- **候補B（Bundle 廃止）**: 複数保存物が夜に自動で束ねられて島のテントや建物になるプロダクト固有の魅力が失われるため却下。
- **候補C（保存直後紐づけなし）**: 「『しまのデモを完成させる』などの明確な Project に保存直後から紐づけて一覧したい」という F03 / F04 要件を満たせないため却下。
