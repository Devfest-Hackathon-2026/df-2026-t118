## 2. 開発の進め方

### 2.1 最初の 7 本の PR は、プロダクトではなく「ハーネス」を作った

実装に入る前に、AI が安全に動ける土台を先に用意した。

| PR | 内容 |
|---|---|
| #3 | 検証の門（`scripts/check.sh`）とガードレール |
| #5 | イシュー実装コマンド `/task` |
| #4 | PR レビューコマンド `/review` |
| #2 | 不在時の一括実行コマンド `/sleep` |
| #6 | メンバー向けオンボーディング |
| #1 / #7 | ドキュメントのトーン統一、提出物の準備 |

ハッカソンで 6 日しかない状況で最初の 1 日を土台に使うのは一見もったいないが、**この後の 27 本の PR がすべてこの土台の上で動いた**。やり直しが減ったぶんで十分に元が取れている。

### 2.2 1 コマンドの門

人も AI も CI も、`bash scripts/check.sh` という**同じ 1 コマンド**を通す。

```bash
bash scripts/check.sh
```

中身は「機密情報がコミットされていないか」＋ 検出したスタックの lint・型・ビルド・テスト。

- **完了の定義は「check が通ること」**。タスク固有の条件も、できる限りテストにして check に入れる
- CI（`.github/workflows/`）はツールチェーンを用意して `check.sh` を呼ぶだけ。チェックを増やすときは `check.sh` だけを編集する
- 失敗したら AI が出力を読んで自分で直し、再実行する。**2 回直しても通らなければ commit せずに報告**する

AI にとって一番つらいのは「完了したかどうかが曖昧なこと」で、ここが曖昧だと「たぶん動きます」という報告が返ってくる。真偽が一意に決まるコマンドを 1 本置くと、それがなくなる。

### 2.3 門は 3 段階に置く

| 層 | 仕組み | 強制力 |
|---|---|---|
| エージェント | `.claude/settings.json` の deny / ask | 迂回できるが即座 |
| リポジトリ | `.githooks/pre-push` → check | `--no-verify` で抜けられる |
| リモート | CI（`check`） | 抜けられない |

`deny` は `rm -rf` / `git push --force` / `.env` の読み取り。`ask` はブランチ削除・`git reset --hard`・クラウドリソースの削除。
**Bash のパターン一致は万能ではない**ので、これは最後の砦ではなく事故防止と位置づけている。ルール本体は `AGENTS.md` にある。

### 2.4 ルールは 1 ファイルに集約する

`CLAUDE.md` と `GEMINI.md` は `AGENTS.md` を参照しているだけで、中身を持たない。

- ルールの変更は `AGENTS.md` だけで行う（エージェントごとにルールが分岐しない）
- マージ条件・レビュー観点・self-review の手順は `.claude/shared/rules.md` に 1 つだけ置き、各コマンドから参照する

同じ内容が 2 箇所にあると、片方だけ古くなって AI がそれを読む。**ルールの重複は、そのままバグになる。**

### 2.5 判断は人間、記録は ADR

`AGENTS.md` に「**人間が決定するまで実装を始めない**」と書き、ライブラリ・フレームワーク・データモデル・外部サービスの選択が必要になったら、AI は次をして止まる。

1. 候補を 2〜3 個
2. pro/con 表（学習コスト / 実装速度 / Google 製品との相性 / コスト / デプロイ容易性 / 情報量）
3. 推奨案と根拠
4. 確証のない情報は「要確認」と明記する

決まったら `docs/decisions/` に ADR を残す（現在 6 本）。ADR-001 は要件を精査する前に技術スタックを決めてしまった失敗で、**1 日で廃止して ADR-002 に差し替えた**。この失敗を消さずに残してあるのは、同じ議論を二度しないためでもある。

### 2.6 「本番で検証した実装状況」を設計ドキュメントより上に置く

AI に書かせたドキュメントは、実装が進むと静かに嘘になる。そこで [`implementation-status.md`](implementation-status.md) を用意し、**本番で動かして確かめた結果だけ**を書くことにした。`AGENTS.md` の参照表でも、このファイルを設計ドキュメントより優先すると明記している。

効果が実際に出た例:

- 「月予算上限 \$3」の表示が実装されていないことを自分で記録し、提出物の文言修正を P1 として積んだ
- 定時バッチが AI クォータを通っていないことを、実装直後に残リスクとして記録した
- 提出書類（`product-doc.md`）を書くとき、この 1 ファイルと照合することで「未実装を実装済みと書く」のを防いだ

### 2.7 1 イシュー 1 PR、worktree で並列

- ブランチ名は `<prefix>/<イシュー番号>-<説明>`
- イシューには**担当者と受け入れ条件**を必ず書く（担当者のないイシューは自動実装の対象にしない）
- 依存は本文に `前提: #12、#15` の 1 行で書く。この行を自動化が読んで、着手可能なイシューを判定する
- 作業は git worktree で分ける。複数のエージェントが同時に別のイシューを触っても衝突しない

### 2.8 レビューは 3 重

1. **self-review** — commit する前に、AI が自分の差分を他人の差分として読み直す。観点は 6 つ（要件充足 / 正確性 / 簡潔さ / セキュリティ・課金 / テスト / 決定の記録）。指摘があれば自分で直し、指摘がなくなるまで繰り返す（最大 3 回）
2. **Gemini Code Assist** — PR に自動で走る
3. **人＋ `/review`** — イシューと照らして指摘を出し、**許可を得てから**投稿する

レビュー専用のサブエージェント（`.claude/agents/reviewer.md`）は `model: sonnet` を指定し、**コードを変更せず・PR に投稿もしない**。権限を絞ることで、レビューと実装が混ざらないようにしている。

### 2.9 不在時は `/sleep` で回す

人が寝ている間、確認を取らずにレビュー・マージ・コンフリクト解消・実装まで進める。ハッカソンの夜を使うための仕組み。

守らせているルール:

- 技術選定が必要になったら**実装せずに止まる**（`skipped` として報告）
- マージ条件（CI 成功・コンフリクトなし・指摘対応済み・機密情報なし）を満たさない PR はマージしない
- force push、他人のブランチの書き換え、イシューのクローズ・編集はしない
- 自分が作った PR は自動マージしない

## 3. 効いた工夫と、効かなかったこと

### 効いた

| 工夫 | なぜ効いたか |
|---|---|
| 完了の定義を 1 コマンドに落とす | 「たぶん動く」報告が消える。AI が自分で直して再実行できる |
| ルールを 1 ファイルに集約 | 重複したルールの片方が古くなる事故が起きない |
| 本番検証の結果を正とするファイル | ドキュメントが静かに嘘になるのを止められる |
| 技術選定で止める規約 | AI が勝手に依存を増やさない。ADR が後から読める |
| 役割ごとにファイルを分けてサブエージェントに 1 つだけ読ませる | 速い・安い・迷わない（後述） |
| ガードレールをコミットする | `clone` した全員に同じ制約が効く |

### 効かなかった・やり直した

- **ADR-001（React Native）** — 提出要件を読む前に技術を決め、1 日で廃止した。**要件の確認を実装判断より先に置くべきだった**
- **AI が書いた手順書が実装とズレる** — ホームのボタン構成を変えた PR（#41）のあと、提出書類の動作確認手順が古いままだった。結局、**本番を実際に操作して手順を書き直した**（この記録自体が 2.6 の裏づけ）
- **生成 AI の出力をそのまま信じる** — 保存物の意図候補は、Gemini の出力が使えないときテンプレートにフォールバックする実装になっており、短いメモだとテンプレート側に落ちて不自然な日本語（14 文字で切った文＋助詞）になることが、本番を触って初めて分かった。**画面を実際に見るまでは「動いている」と言わない**

## 4. トークン制限の中での工夫

### 4.1 まず実測する

この作業セッション 1 本の内訳（コンテキスト 290,008 / 1,000,000 トークン使用時点）:

| 区分 | トークン | 割合 |
|---|---:|---:|
| 会話（メッセージ） | 211,521 | 21% |
| システムツール定義 | 29,545 | 3% |
| MCP ツール定義 | 24,119 | 2% |
| システムプロンプト | 12,806 | 1% |
| スキル | 6,842 | 1% |
| MCP サーバーの説明文 | 3,841 | 0% |

**会話を 1 文字もしていない時点で、約 57,000 トークン（ツール定義＋MCP）が乗っている。** 使わない MCP サーバーを繋いだままにすると、その固定費を毎セッション払うことになる。

アカウント側の実測（同時点）: 週の利用枠 66%、追加利用枠 \$69.71 / \$70（99%）。
**6 日の開発で、追加利用枠をほぼ使い切った。** 節約は「気をつける」ではなく、仕組みで落とす必要がある。

### 4.2 すでにやっていること

1. **サブエージェントには 1 ファイルだけ読ませる**
   `.claude/commands/sleep.md` は親（オーケストレーター）の手順だけを持ち、実作業の手順は役割別ファイル（`.claude/sleep/review.md` など）に分けてある。親は手順を書き写さず、**ファイルのパスと対象だけ**を渡す。
   サブエージェントのプロンプトに含めるのは 4 つだけ: ①役割ファイルのパス ②対象（PR / イシュー番号） ③原則の要約 ④報告の形。

2. **モデルを作業の重さで使い分ける**
   判断の軽い定型作業（マージ条件の確認）は軽いモデル、レビュー・実装・コンフリクト解消は親と同じモデル。レビュー専用エージェントは `model: sonnet` で固定。

3. **並列は 3 つまで、バッチではなくローリング**
   完了通知を受けるたびに次を起動する。同時に 10 本走らせても、結局どれも中途半端になる。

4. **検証を 1 コマンドにまとめる**
   `check.sh` の出力は短く、成否が一意。AI が「どうやって確認するか」を毎回考えない。テストにできる条件はテストにする（＝短い出力で真偽が出る）。

5. **現状を 1 ファイルに集約する**
   新しいセッションに設計ドキュメント一式を読ませる代わりに、`implementation-status.md` 1 本を読ませれば「今どこまで動いているか」が分かるようにしてある。

6. **決定を ADR で固定する**
   同じ技術議論を二度しない。これは品質のためでもあるが、トークンのためでもある。

7. **Plan モードで方針を合意してから実装する**（`CLAUDE.md`）
   手戻りがいちばん高くつく。構成や設計に関わる変更は、書き始める前に方針を出す。

### 4.3 これからやること（優先順）

| # | やること | 効き方 |
|---|---|---|
| 1 | **使わない MCP サーバーを切る** | セッションあたり固定で数万トークン減る。接続しているだけで課金対象のコンテキストを食う |
| 2 | **ファイルは「探してから部分だけ読む」** | `grep` で行番号を出してから範囲読みする。大きいファイルを丸ごと読むのが最大の無駄 |
| 3 | **画面の確認はテキストを先に、画像は最後に** | ページのテキスト抽出やアクセシビリティツリーは安く、スクリーンショットは高い。見た目の最終確認だけ画像にする |
| 4 | **セッションをタスク単位で切る** | 1 本の会話を引きずるほど、毎ターン過去全部を読み直すことになる。タスクが変わったら新しいセッションにする |
| 5 | **失敗を記録して二度繰り返さない** | `implementation-status.md` の「残っていること」に、未確認・未解決をそのまま書く。同じ調査を次のセッションがやり直さない |
| 6 | **定型作業をコマンド化する** | `/task` `/review` `/sleep` のように手順をファイルにしておくと、毎回手順を説明し直さなくて済む |
| 7 | **報告の形を決めておく** | 「返す報告の形」を役割ファイルに書いておくと、長い報告が返ってこない |

### 4.4 考え方

トークンの節約は「短く書く」ことではなく、**読ませる量を設計すること**に尽きる。

- ルールは 1 箇所（`AGENTS.md`）
- 現状は 1 ファイル（`implementation-status.md`）
- 完了は 1 コマンド（`check.sh`）
- 手順は役割ごとに 1 ファイル（`.claude/sleep/*.md`）

この「1 つにする」設計は、結果としてトークンも、人間が読む手間も、両方減らしている。

## 5. 真似するときの最小セット

このリポジトリから持っていくなら、この 4 つで足りる。

1. `scripts/check.sh` — 完了の定義を 1 コマンドにする
2. `AGENTS.md` — ルールを 1 ファイルに集約し、`CLAUDE.md` / `GEMINI.md` から参照する
3. `.claude/settings.json` — `rm -rf` / force push / `.env` 読み取りを deny、破壊的操作を ask
4. 「本番で検証した実装状況」のファイル — 設計ドキュメントより優先すると宣言しておく

残り（`/task` `/review` `/sleep`、worktree 並列、ラベル運用）は、人数とタスクの数が増えてから足せばよい。
