# 共通規則（マージ条件・レビュー観点・ラベル）

`.claude/sleep/*.md` の各役割から参照する。

## マージ条件

次のすべてを満たすときだけマージする。1つでも欠けたらマージせず、理由を報告する。

- CI（`check` = `scripts/check.sh`）が成功している。pending の場合は最大5分待ち、それでも終わらなければ `ci_pending` に記録して見送る
- `mergeable` が `MERGEABLE`（コンフリクトなし）
- Draft でない
- レビューの指摘がすべて対応済み、または「対応不要」と判断でき、その理由を説明できる
- `.env` や API キー・認証情報を含む差分がない（`git diff` で確認。CI の `.env` チェックに頼りきらない）
- `docs/architecture.md` や `docs/decisions/` の ADR と矛盾しない

> `main` は private + GitHub Free のためブランチ保護が効かない。GitHub 側が止めてくれないので、上の条件は自分で確認する。

マージ方法は squash（`gh pr merge <番号> --squash --delete-branch`）。

## 検証

- 検証は `bash scripts/check.sh` の1コマンド。人もAIもCIも同じ門を通る
- 実装・レビュー対応・コンフリクト解消のあと、コミット前に必ず通す
- 完了の定義は「check がすべて通ること」。失敗したら出力を読んで自分で直し、再実行する
- 2回直しても通らなければ、commit せずに報告する

## self-review

commit する前に、自分の差分を他人の差分として読み直す。

```bash
git diff origin/main...HEAD   # 未コミット分も含めて確認する
```

観点:

1. **要件充足**: イシューの受け入れ条件を満たしているか
2. **正確性**: バグ、考慮漏れ、エラー処理の抜け
3. **簡潔さ**: 冗長なコード、不要な抽象化、無駄なコメント
4. **セキュリティ・課金**: 機密情報の混入、外部入力の未検証利用、ループ内のAPI呼び出し
5. **テスト**: 必要なテストがあるか、check に入っているか
6. **決定の記録**: 実装中に決めたことが PR 本文か ADR に書かれているか

- 推測で指摘しない。コードで確認できた問題に絞る
- 指摘があれば同じブランチで自分で直し、check を通してからもう一度読む。指摘がなくなるまで繰り返す（最大3回。それでも残る場合は報告に明記する）

## レビュー観点（優先順）

1. 機密情報の混入（API キー、認証情報、`.env`）
2. 動作不良・データ破壊につながるバグ
3. セキュリティ上の問題（外部入力を検証せず利用する、URL 取得先の制限なし、など）
4. 想定外の課金につながる実装（ループ内の API 呼び出し、リトライの上限なし、常時起動型サービスの追加）
5. 要件・ADR との不整合（`docs/requirements.md` のスコープ外の実装、ADR と異なる技術の持ち込み）
6. 保守性（責務の分離、関数の長さ、命名）

スタイルの好みに関する指摘はしない。
Gemini Code Assist が同じ点を既に指摘している場合は重複して書かず、「Gemini の指摘に同意」と一言で済ませる。

## 指摘の書き方

指摘1件ごとに、次の4つを書く。観点は上の優先順リストを次の5つに畳んだもの。

- **ファイルパス:行番号**
- **観点**: 要件 / 正確性 / セキュリティ・課金 / テスト / 決定の記録
- **問題**: 何が問題か（理由まで）
- **修正案**: 具体的にどう直すか（必要ならコード例）

行コメント付きで1つのレビューとして投稿する場合:

```bash
gh api repos/{owner}/{repo}/pulls/<番号>/reviews --method POST --input - <<'JSON'
{
  "body": "<総評>",
  "event": "COMMENT",
  "comments": [
    { "path": "src/foo.ts", "line": 42, "side": "RIGHT", "body": "<指摘>" }
  ]
}
JSON
```

`line` は差分に含まれる行番号。差分外の行を指定するとエラーになるので、その指摘は総評（`body`）に書く。

## 状態ラベル

| ラベル | 意味 | 付ける人 |
| --- | --- | --- |
| `status::wip` | イシューの実装中、またはPRのレビュー対応中 | 作業を始める人 |
| `status::reviewing` | PRのレビュー中、またはマージ確認中 | レビューする人 |

- 作業を始めるときに付け、終わるとき（成功・失敗・中断のどれでも）に必ず外す。
- **他のメンバーが作業中かの判定**: ラベルが付いていて、かつそのPR・イシューの `updatedAt` が1時間以内なら作業中とみなし、触らない。1時間を超えて残っているものは残骸として扱い、対象にしてよい（ただし他人のラベルは外さない）。

## 技術選定が必要になったとき

`AGENTS.md` の「人間が決定するまで実装を始めない」が常に優先される。実装中にライブラリ・フレームワーク・データモデル・外部サービスの選択が必要になったら、

1. その場で決めず、作業を止める
2. 候補 2〜3 個と pro/con（学習コスト / 実装速度 / Google 製品との相性 / コスト / デプロイ容易性 / 情報量）をまとめる
3. 親に「技術選定が必要」として報告する。コードは commit しない（途中まで書いたものは捨てる）

既に ADR で決まっている範囲内の判断（決定済みフレームワークの標準的な書き方など）は、選定には当たらないので進めてよい。

## 決定の記録

実装中に ADR に書かれていない設計判断をした場合は、PR 本文の「背景・理由」に残す。ADR が必要なレベル（他の実装を縛る、後から変えにくい）と判断したら、`docs/decisions/` への追加を最終報告で提案する（自分で ADR を確定させない）。
