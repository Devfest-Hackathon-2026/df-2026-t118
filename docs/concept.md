## 1. 先行事例の分解

### 観察

| 画面 | やっていること |
|---|---|
| オンボーディング | 普段使う SNS を聞く / 動画 1 件からレシピを抽出して見せる |
| 目標設定 | 「保存したレシピを1つ作る」など定型の週次ゴールを選ばせる |
| 宣言 | 「ため込むためじゃなく、やるために保存する」と約束させる |
| 将来像 | 「3ヶ月後、約150件の保存 — ひとつ残らずコレクションの中に」 |
| 詳細画面 | 要約の箇条書き、材料、手順、形式/ソース/読了時間、タグ |
| ホーム | カテゴリ別コレクションのグリッド（その他 1・記事 1・レシピ 0 …） |

### 構造的な問題

**(a) 保存を資産として扱っている**

「3ヶ月後に約150件」を成果として提示する一方、直前の画面で「ため込むためじゃなく、やるために保存する」と言わせている。指標が自己矛盾していて、アプリが報酬を与えているのは保存であって実行ではない。保存が増えるほど未消化の負債と罪悪感が増える。

→ **誇るべき数字は保存数ではなく消化数。** 「今月 7 件保存して 5 件やった」が出る設計にする。保存を抑制する提案（「これは似たものを3件持ってる。保存しないで今日やる？」）ができてもいい。

**(b) 構造化の粒度が意思決定の粒度と合っていない**

材料一覧と手順は「作ると決めた後」に要る情報。ユーザーが詰まっているのは決定の手前で、そこで要るのは別の情報 — 今から何分かかるか、手持ちとの差分は何か、誰と食べるのか、前に似たものを作って良かったか。

**AI は「実行の情報」を出しているが、ユーザーが止まっているのは「決定」。これが「それで何？」の正体。**

→ 構造化の出力を決定支援に寄せる。

| 今 | 変更後 |
|---|---|
| 材料: ペンネ 400g / にんにく 2かけ / トマトパッサータ 400g / バジル | 今日あと 25 分。足りないのはパッサータだけ。帰り道のスーパーで買える |

**(c) 質問がアプリのためのもので、ユーザーに何も返らない**

「役立つコンテンツは、普段どこで見つけますか？」はアンケートであって対話ではない。答えても何も準備されない。「保存したレシピを1つ作る」も、ユーザーから出てきた目標ではなくアプリが用意した選択肢。

→ **エージェントの質問は、答えたら必ず何かが準備されるものだけにする。**

**(d) 一件ずつしか見ていない**

1 件の保存は意図として読めないが、「2週間で時短パスタを5件」は読める。群で見ないと意図は取り出せない。

## 2. このプロダクトの立て方

### 前提の置き換え

> **保存はコンテンツではなく、言語化されていない意図の断片である。**

エージェントの仕事は、保存を綺麗に並べることではなく、断片から意図を推定し、最小の質問で確かめ、ユーザーの現実の状況に接地した次の一手に変換すること。

### 3 層モデル

| 層 | 中身 | 誰が作るか |
|---|---|---|
| 保存 (signal) | URL・動画・そこから抽出した構造 | 抽出エージェント（先行事例と同等。差別化要素ではない） |
| 意図 (intent) | 「平日の夕飯に困っている」「次の京都旅行の下調べ中」 | 推定エージェント + ユーザーへの確認 ← **ここが本体** |
| 行動 (action) | 「金曜 19:00、買い足し1点で作れる1品」 | 立案エージェント + 承認後の実行 |

先行事例は保存層で止まり、意図層を飛ばして行動層に定型ゴールを置いた。だから刺さらない。

## 3. エージェントのループ

```
観測 → 仮説 → 質問（分岐が変わるときだけ） → 提案 → 準備 → 実行 → 学習
  ↑                                                              │
  └──────────────────────────────────────────────────────────────┘
```

### 設計原則

**1. 質問は「AI が知らないこと」ではなく「答えで提案が変わること」だけ聞く**

情報利得で質問を選ぶ。どの答えでも同じ提案になるなら聞かない。質問はできるだけ仮説をぶつける閉じた形にする。

```
✗ どんな料理が好きですか？
✓ 時短レシピを今月5件保存してる。平日の夜ごはん、困ってる？
   [そう] [違う、週末用] [今は見てるだけ]
```

**2. 単品ではなく群から読む**

保存履歴をクラスタリングし、パターン単位の仮説を出す。「よく見てるな」と思わせるのはこれ。1 件ずつの要約では絶対に出ない。

**3. 提案は今の状況に接地させる**

接地させる軸: 時間（カレンダーの空き）/ 場所 / 手持ち（在庫・買い物）/ 体力・気分。ハッカソンの最小構成はカレンダー + 曜日時間帯。

**4. 承認の粒度を3段に分ける**

| 粒度 | 対象 | UI |
|---|---|---|
| 黙ってやる | 整理・分類・下書き生成・候補の下準備 | 事後報告のみ |
| 軽く確認 | 提案の採否 | 1 タップ |
| 必ず承認 | 外部サービスへの書き込み・送信 | 内容を見せて明示的に承認 |

`docs/requirements.md` の自律レベル 1〜4 にそのまま対応する。

**5. 却下こそ学習材料**

「今週は無理」は失敗ではなく制約の獲得。再提案する前に、なぜ無理だったかを 1 問だけ聞いてユーザーモデルに入れる。「平日夜は提案しない」が蓄積されていくほど、エージェントが自分を知っていく感覚が出る。

**6. 能動性 = ユーザーがアプリを開いていない時に考えていること**

保存した瞬間に反応するのはただの処理。3 日後に「先週保存したカフェ、土曜の午後に予定が空いてる。行く？」と自分から来るのが能動。定期実行で仮説を更新し、確度が閾値を超えたときだけ通知する。

## 4. 画面の方針

ホームをコレクションのグリッドにしない。グリッドは未消化の山の可視化であり、負債の陳列になる。

**ホーム = いまエージェントが考えていること 1 枚。**

```
🦝 気づいたこと
「時短パスタ」を今月5件保存してる。
平日の夜ごはん、困ってる？
                    [そう] [違う、週末用] [今は見てるだけ]
```
↓
```
じゃあ金曜 19:00 に 1 品決めとく。
手持ちで作れるのはこの 2 つ。足りないのは生クリームだけ。
                    [これにする] [別の日] [今週はパス]
```

対話は 2 往復まで。各ターンが必ず具体物（予定・買い物リスト・リマインド）で終わる。コレクション一覧は検索用に残すが、主役から外す。

## 5. ハッカソン向けの構成案

技術の最終決定は `docs/tech-selection.md` と ADR に従う。ここでは役割分割のみ示す。

| エージェント | 役割 | 差別化 |
|---|---|---|
| Extractor | URL・動画 → 構造化 | なし（土台） |
| Profiler | 保存履歴の群 → 意図仮説・ユーザーモデル更新 | **中核** |
| Interviewer | 不確実性の高い分岐だけ質問を生成 | **中核** |
| Planner | 仮説 + 空き時間 + 制約 → 実行可能な行動案 | 高 |
| Executor | 承認後にカレンダー・ToDo へ書き込み | 中 |

起動契機を 2 つ持つのが要点。

1. 保存時（同期）: 抽出して仮説を更新するだけ。通知しない
2. 定期実行（非同期）: 仮説を見直し、確度が閾値を超えたら通知 ← **能動性の実体**

### MVP の切り方（提案）

- ドメインを 1 つに絞る（レシピ or おでかけ）
- 保存 10〜15 件をシードデータとして用意し、群から仮説が立つ状態を作る
- 自律レベル 3 を本線、4（カレンダー書き込み）をデモの山場に置く
- 外部連携は Google カレンダー 1 つだけ

### デモシナリオ（案）

1. 動画を 1 件保存する。エージェントは抽出だけして黙る（ここで「それで何？」を意図的に体験させる）
2. 画面を閉じる。定期実行が走る
3. 通知: 「時短レシピを今月5件保存してます。平日の夜ごはん、困ってます？」
4. [そう] → 「金曜19時が空いてる。手持ちで作れるのはこれ。足りないのは1点だけ」
5. [これにする] → 承認画面 → カレンダー登録 + 買い物リスト生成
6. ホームの数字が「保存 5 / 実行 1」に変わる

1 の「黙る」が効く。先行事例との差をその場で体験させられる。

## 6. 決めてほしいこと

| 論点 | 選択肢 | 影響 |
|---|---|---|
| 対象ドメイン | レシピ / おでかけ・旅行 / 学習コンテンツ / 絞らない | 絞らないと群から意図が読めず、中核が成立しない |
| 想定ユーザー | 保存癖のある人の中で、どの属性に寄せるか | 仮説の精度とデモの説得力 |
| 目標自律レベル | 3（準備まで）/ 4（承認後に実行） | 実装コストとデモの山場 |
| 入力経路 | 手動 URL / モバイル共有シート / ブラウザ拡張 | 共有シートが本来の体験に最も近いが実装コストが上がる |
| 能動通知の契機 | 定期実行 / 保存件数の閾値 / 両方 | 「自律エージェント」としての見え方を左右する |
| 対話の深さ | 1 往復 / 2 往復 / 可変 | UI 量と実装量 |
