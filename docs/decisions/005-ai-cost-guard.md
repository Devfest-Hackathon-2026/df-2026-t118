# ADR-005: 不特定多数にログインされたときの AI 課金ガード

- 日付: 2026-11-09
- 状態: 承認
- 決定者: Kambara-Michiru

## 背景

本番（https://hannari-hustlers.web.app）は匿名認証で誰でも入れる。大規模ハッカソンで公開する前提なので、
不特定多数に叩かれたときの Gemini API の課金と、レート上限に当たってデモが落ちることを考える必要があった（イシュー #38）。

コードを読んで確認した、着手前の状態:

- ADR-003 で入れた callable の `requireUid` は**課金ガードとして機能しない**。匿名 uid はタダで無限に作れる
- `NightOrganizeInputSchema.items` に件数の上限がなく、埋め込みが `Promise.all` で**無制限に並列**になる。
  1 リクエストで数千回の Gemini 呼び出しを起こせた
- `imageDataUrl` / `rawText` にも上限がなく、callable の 10MB まで積めた
- レート制限が per-uid も per-IP も無く、実質「無料の Gemini プロキシ」だった
- `onCall` / `onSchedule` に `maxInstances` などの指定が 1 つも無く、並列に張り付かれると課金もスケールした
- UI の「月予算上限 $3」は**表示だけで止まらない**。判定に使う `estimatedUsedUsd` はクライアント側の定数 `0.04`

制約は提出要件 4（デプロイ URL を 2026-11-14 まで稼働）と、提出が 2026-11-10 19:00 であること。
**課金停止でサービスを落とすことは選べない。** つまり必要なのは「請求を止める仕組み」ではなく
「上限に当たっても静かに劣化して動き続ける仕組み」だった。

## 候補と比較

- **案A: 設定と入力上限だけ** — `maxInstances`、zod の `.max()`、並列度の上限、予算アラート
- **案B: A ＋ サーバー側の日次クォータ＋キルスイッチ** — per-uid と全体のカウンタを Firestore に持つ
- **案C: B ＋ App Check を適用（enforce）** — 「自分のアプリから来たか」をサーバーで検証する

| 観点 | 案A | 案B | 案C |
|---|---|---|---|
| 学習コスト | ほぼ 0 | 低（`FieldValue.increment` とトランザクションだけ） | 中（reCAPTCHA キー・デバッグトークンの設定） |
| 実装速度 | 30 分 | +1〜2 時間 | +1〜2 時間＋検証 |
| Google 製品との相性 | ◎ | ◎（Firestore だけで済む） | ◎（Firebase 純正の答え） |
| コスト | 0 | AI 呼び出し 1 回につき Firestore の read/write が数件増える | 0 |
| デプロイ容易性 | ◎ | ◎ | **△ 設定の取りこぼしで本番の AI が全滅する** |
| 情報量 | 多い | 多い | 多いが、匿名認証と組み合わせた事例は少ない |

## 決定

**案B を実装し、App Check は「登録と計測だけ・未適用（monitor）」までにする。** 適用は提出後（11/10 夜以降）。

入れたもの:

1. **ランタイムの天井** — callable 5 本に `maxInstances: 10` / `timeoutSeconds: 60` / `memory: '512MiB'`、
   定時バッチ 2 本に `maxInstances: 1` / `timeoutSeconds: 540`。`concurrency` は指定しない
   （gen2 は CPU 割り当てと連動し、誤るとデプロイが失敗する）
2. **入力の上限** — `functions/src/domain/schemas.ts` に `.max()`。保存物 200 件、画像 3,000,000 文字、
   本文 50,000 文字、ターゲット 50 件など。正当なクライアントが踏まない線に取る
3. **実処理量の上限** — `runNightOrganize` は先頭 40 件だけを AI に回し、埋め込みは 4 件ずつ流す
4. **日次クォータ** — `functions/src/application/aiQuotaUseCases.ts`。per-uid 300 / 日、全体 20,000 / 日（既定値）。
   `config/aiGuard` ドキュメントで上書きでき、`disabled: true` が全体のキルスイッチ
5. **App Check** — サイトキーが設定されている環境でだけクライアントが初期化する。サーバーは検証しない

`.transform()` での切り詰めは使わなかった。`ZodEffects` になると Genkit の `inputSchema` 変換に通らない恐れがあるため。

## 根拠

- **止めるのではなく劣化させる。** 上限に当たった呼び出しは `resource-exhausted` で弾くが、クライアントは
  `/api` → `httpsCallable` → ローカルエンジンの順に落ちる（`src/infrastructure/ai/aiFlowClient.ts`）。
  画面は止まらず、AI の文面がテンプレートに替わるだけになる。提出要件 4 を壊さない
- **フェイルオープンにした。** カウンタの読み書きが失敗したら通す。ガードの故障で本番の AI が全滅するほうが、
  多少の課金より損が大きい。実際の防波堤は `maxInstances` と入力上限と合わせた多層で持つ
- **per-uid の上限を 300 と高めに取った。** ここに当たるとテンプレート文が出て「AI が動いていない」ように
  見えるため、低く絞りすぎるほうが審査では危ない。悪用の抑止は入力上限と `maxInstances` が担う
- **全体カウンタだけ厳密にしない。** 単一ドキュメントに毎回トランザクションを張ると Firestore の
  1 ドキュメントあたりの書き込み制約に当たる。30 秒キャッシュした読み取り＋`increment` にして、多少の超過を許す
- **App Check の適用を提出後に回した。** 効果は最大だが、提出前日に enforce して設定を取りこぼすと
  本番の AI が全滅する。登録して計測だけ溜め、提出後に切り替えるほうが期待損失が小さい

## 却下した案と理由

- **案A だけ** — 1 人が毎日叩き続ける経路が残る。カウンタが無いと「誰がどれだけ使ったか」も分からず、
  当日の被害も事後に説明できない
- **案C を今日入れる** — 上記のとおり、提出前日の enforce は事故ったときの損が大きすぎる
- **予算アラートだけに頼る** — 通知は事後で、止めてはくれない。天井としては使えない
- **ドル建ての従量カウンタをサーバーで積む** — トークン数から金額を推定する精度がなく、外部検索も
  まだ固定データ（`curated_reference_fixture`）なので、金額の精度はいまのところ見かけ倒しになる。
  「回数」で数えるほうが実態に合う

## 残っているリスク

- **定時バッチはクォータを通っていない。** callable を経由せずユースケースを直接呼ぶため、カウンタを
  進めも読みもしない。バッチの量は `listUserIds(100)` と件数上限で決まるので当面は放置するが、
  「全体 20,000 / 日」にバッチぶんは含まれていない
- **匿名 uid の量産には無力。** 1,000 個の uid を作れば 300,000 回ぶんの天井になる。塞ぐのは App Check（適用後）
- **全体の天井に当たると全員が劣化する。** 自分のデモを人質に取られうるが、請求が無限に伸びるほうを避けた
- **UI の「月予算上限 $3」は依然として表示だけ。** 実際のガードは per-uid の日次回数であり、
  `docs/island-growth-story.md` の「自動でストップする安心設計」という記述は実装と合っていない（要文言修正）

## 人間の作業（コンソール）

1. **予算アラート** — Cloud Billing で予算を作り、50% / 90% / 100% で通知する（止めてはくれない前提）
2. **Gemini のクォータ確認** — Google AI Studio のクォータ画面で、このプロジェクトの RPM / TPM / RPD の実値を見る。
   「何人同時で 429 になるか」はここ次第。公式ドキュメント以外の数字は信用しない
3. **App Check の登録（適用はしない）**
   - reCAPTCHA v3 のサイトキーを発行する
   - Firebase コンソール → App Check → ウェブアプリを登録し、**API は「未適用」のまま**にする
   - `.env` と Hosting のビルド環境に `VITE_FIREBASE_APPCHECK_RECAPTCHA_KEY` を設定する
   - `.env.example` に `VITE_FIREBASE_APPCHECK_RECAPTCHA_KEY=` の行を追記する
     （エージェントの権限設定で `.env*` の読み書きが禁止されているため、この 1 行は人間が追記する）
   - 提出後、計測データを見て問題がなければ適用に切り替える
4. **緊急停止** — Firestore の `config/aiGuard` に `{ disabled: true }` を書くと、全ユーザーの AI が止まり
   ローカルエンジンに落ちる。`{ userDailyLimit: 50 }` のように上限だけ下げることもできる
